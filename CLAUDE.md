# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

This is the **laurigates/.github** repository — a special GitHub repo that provides default community health files and reusable GitHub Actions workflows for all [@laurigates](https://github.com/laurigates) repositories. It contains no application code, build system, or tests.

## Repository Structure

- **Root files** (`CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`, `SUPPORT.md`) — default community health files inherited by all laurigates repos unless overridden
- **`profile/README.md`** — GitHub profile page content
- **`.github/ISSUE_TEMPLATE/`** — default issue templates (bug report, feature request)
- **`.github/PULL_REQUEST_TEMPLATE.md`** — default PR template
- **`.github/workflows/reusable-*.yml`** — reusable workflows (the main deliverable of this repo)

## Workflow Architecture

All workflows are **reusable** (`workflow_call`) and called from other repos via:
```yaml
uses: laurigates/.github/.github/workflows/reusable-<name>.yml@main
```

### Runner selection: `ubuntu-slim` for API-only jobs

Jobs whose entire body is GitHub-API churn — `gh` calls, `actions/github-script`,
`create-github-app-token`, release-please, label/PR bookkeeping — run on
**`ubuntu-slim`** (1 CPU, $0.002/min vs $0.006/min). Everything else stays on
`ubuntu-latest`.

`ubuntu-slim` is an *unprivileged container*, not a VM, and carries no hosted
tool cache. It therefore **cannot** run:

- anything needing a Docker daemon — including actions that only *look* like
  plain composites: `renovatebot/github-action`, `trufflesecurity/trufflehog`,
  `pypa/gh-action-pypi-publish` (`gitleaks/gitleaks-action` is `node24`, so it
  is fine)
- `container:` / `services:` jobs, `sudo`/`apt-get`, mounts, kernel features
- Go, Rust, Java/Gradle/Maven, .NET, Ruby, PHP, Swift, Android, browsers,
  databases, kubectl/helm, CMake/Bazel, CodeQL — none are preinstalled

Preinstalled and safe to rely on: bash, Node 24, Python 3.12, gcc/g++, git+LFS,
`gh`, jq, yq, curl, zstd, AWS/Azure/gcloud CLI. `actions/setup-node` /
`setup-python` still work but must *download* the runtime (no tool cache), so
prefer slim for jobs that don't need one.

When a job in a reusable workflow is split (a cheap gate + an expensive Claude
step), put only the gate on slim — see `reusable-changelog-review.yml` and
`reusable-auto-resolve-conflicts.yml`.

### Container Build/Release (build-once/promote pattern)

The container workflows implement a two-phase pattern:

1. **`reusable-container-build.yml`** (PR phase) — builds and pushes a `:next-{version}` pre-release image to GHCR during the release-please PR
2. **`reusable-container-release.yml`** (tag phase) — resolves a single release *candidate* (promoted `:next-{version}` digest, or a rebuild), scans it, and only then creates the release tags. Optional cosign keyless signing via Sigstore

The version is extracted from the version file (default: `package.json`) during build, and from the git tag (stripping `tag-prefix`) during release.

#### The vulnerability scan is a publication gate, not a report

The release job's invariant: **exactly one step creates a release tag, it has no `if:`, and the step immediately before it is the scan.** The scan's subject is a digest resolved by a step that also has no `if:` and hard-fails when it cannot resolve one, so both the promote and the rebuild path are covered by construction rather than by a condition someone can get wrong.

Five things not to re-derive:

- **The rebuild path pushes to `:next-{version}`, never to `meta.outputs.tags`.** Pushing the release tags from `docker/build-push-action` is what made the old scan unable to gate anything — the artifact was already published by the time it ran. Release tags are applied by `docker buildx imagetools create` from the scanned digest
- **The scan lives in `.github/actions/scan-image` and must be referenced fully-qualified** (`laurigates/.github/.github/actions/scan-image@main`). A `./`-relative `uses:` inside a reusable workflow resolves against the *caller's* checkout and fails in every consumer. It enumerates platform manifests from the image's own index, so a multi-arch caller's arm64 layers are scanned without anyone passing `platforms` twice
- **`--exit-code 13`, not `1`.** Trivy exits with the requested code for findings (`types.ExitError`) and `1` for everything else (`log.Fatal`), so `1` makes a DB-pull failure indistinguishable from a real CVE — and the natural response to the former is to switch the gate off. Confirmed on the pinned `v0.70.0` binary
- **The promote wait and the digest resolution are the same step, and the digest comes out of the wait's own probe.** `pr-image` waits for the PR-phase build (issue #51) and resolves `:next-{version}` to a digest in one place, which is the only read of that mutable tag in the job — freshness, the scan and publication all address the digest, so a concurrent PR-phase build moving the tag mid-job cannot change what ships. Editing the wait means preserving `PROBE_DIGEST`; editing the digest handling means preserving the bounded wait
- **`scan-enforcement` is a validated string (`block`|`warn`), not a boolean.** An unrecognised value is a hard error at the top of the job; `continue-on-error: ${{ inputs.scan-enforcement == 'warn' }}` then means anything that is not exactly `warn` blocks. `warn` publishes *and* fails the job, reproducing the pre-gate outcome rather than swallowing the failure into a green run

The PR-phase build's scan is **advisory by default** (`scan-mode: advisory|block|off`) and is not the gate: a CVE published against an unchanged base would otherwise block every unrelated release, and the rebuild path exists precisely when the PR image is not what ships. `scan-mode` is validated at the top of the build job for the same reason `scan-enforcement` is — its `continue-on-error: ${{ inputs.scan-mode != 'block' }}` fails *open*, so an unvalidated `blocking`/`enforce`/`true` would silently downgrade a caller's blocking check to advisory.

### Release Automation

- **`reusable-release-please.yml`** — wraps `googleapis/release-please-action`, requires a PAT (`MY_RELEASE_PLEASE_TOKEN`) since GITHUB_TOKEN can't trigger downstream workflows. Carries a **missed-release guard**: when the action reports neither `prs_created` nor `releases_created`, a follow-up step compares `github.event.before...github.sha` via the GitHub compare API and annotates (or fails, per `missed-release-check`) if the range held commits matching `releasable-types`. This exists because release-please's conventional-commit parser can throw on a squash body — repos with `squash_merge_commit_message = PR_BODY` inherit the PR description as the commit body, and a fenced code block there discards *every* commit in the range while the run stays green (issue #40). The guard only catches the all-or-nothing case; the root-cause fix is per-repo `squash_merge_commit_message = COMMIT_MESSAGES` in gitops

  Also **assigns the release PR** (`pr-assignees`, defaulting to `github.repository_owner`). release-please has no native assignee config, and its PRs are bot-authored and mention no one, so they match none of GitHub's dashboard/mobile feeds — not `author:@me`, not `review-requested:@me`, not even `involves:@me`; an assignee is the only thing that files them under a human. Two things not to re-derive: **`@me` is unusable** — `gh` resolves it to the *token* owner, which is the App bot whenever `app-id` is set — and the step must run *before* the missed-release guard, since `missed-release-check: error` would otherwise skip it. It reads `steps.release.outputs.prs` (set on create *and* update, one entry per package in manifest mode) and falls back to listing open `release-please--branches--*` PRs when that output is empty, so an already-open PR still gets assigned. Assign failures warn rather than fail the release. Set `pr-assignees: none` to opt out — `''` cannot be the opt-out because it means "fall back to the owner"
- **`reusable-fix-release-conflicts.yml`** — detects conflicted release-please PRs, closes them, deletes the branch, and retriggers release-please to recreate cleanly
- **`reusable-clear-autorelease-labels.yml`** — manual escape hatch (`workflow_dispatch` caller) that strips a stale `autorelease: pending` label from closed PRs. When the release/tag step fails, the merged release PR keeps the `pending` label and every subsequent run re-attempts the same failed release; clearing it lets release-please move on. Supports a `dry_run` input
- **`reusable-auto-merge-image-updater.yml`** — creates, approves, and auto-merges ArgoCD Image Updater PRs in a single job (workaround for GITHUB_TOKEN anti-recursion)

### Claude-Powered Workflows

- **`reusable-claude.yml`** — enables `@claude` mentions in issues and PRs. Supports configurable runner, max turns, and system prompt for CI turn budget awareness. Posts continuation comments on max-turns exhaustion
- **`reusable-claude-review.yml`** — automated PR review using Claude Code. Skips release-please PRs and bot actors by default
- **`reusable-auto-fix.yml`** — analyzes failed CI workflows and either auto-fixes (commit + push) or opens a GitHub issue. Includes recent-fix detection to prevent loops. Its tool list was inert (see the trap below), which silently disabled the commit/push and issue-creation the workflow exists for; it also never forwarded `actions: read`, so Claude could not read CI results either

  **One failure, one issue.** Before the agent runs, a bash + jq step hashes the failure's most specific log line into a 12-hex signature, and the next step lists open issues for the hidden body marker `<!-- auto-fix-signature: <sig> -->`. A match gets a comment quoting the hashed line, and the prompt's `directive` output forbids a new issue; otherwise the directive has the agent end the new issue's body with the marker. Whenever the lookup's mode is not `create`, `--disallowedTools` also denies `gh issue create` and `gh issue new`. Without this, laurigates/dotfiles collected eight issues (#414-#429) for one broken `uses:` ref. Three things not to re-derive:
  - **The lookup reads the repository issue listing, not the search API.** `gh issue list` without `--search` queries GraphQL `repository.issues`, which shows an issue as soon as it exists; the search index lags creation, and duplicates here were filed minutes apart
  - **`max_auto_fix_prs` counts open issues with a well-formed marker and pauses issue creation only**, never the auto-fix. It used to count open PRs from `auto-fix/*` branches (`head:` is a prefix match), which this workflow never opens (it pushes to the failing branch), so it never fired
  - **`.github/tests/auto-fix-dedup/run.sh` extracts the shipped step bodies** and runs them against real `--log-failed` output (`just autofix-fixtures`); it also checks that every `steps.<id>.outputs.<key>` resolves, because a mistyped one evaluates to '' and silently turns dedup off. It also asserts that no `run:` body in the job contains `${{` and that `Gather failure context` binds `branch`, `run_id` and `pr_number` through `env:`, because a branch name is caller-controlled text (a fork author chooses it) and an inline expansion is script injection (issue #69). Add a fixture there when a new failure shape is mis-grouped
- **`reusable-auto-resolve-conflicts.yml`** — on each push to the base, merges the base into every conflicting PR and has Claude resolve the conflicts. On laurigates/mcu-tinkering-lab it resolved a PR stacked on an already squash-merged PR by keeping both copies of the same change. The result defined a static variable twice, the agent pushed it itself, and no CI ran on the new head (issue #76). Seven things not to re-derive:
  - **A stacked-after-squash PR is detected before the merge, then commented on and never merged.** The primary signal is GitHub's commit→PR association: a branch commit that belongs to another PR with `merged_at` set *and `base.ref` equal to this PR's base* (a PR merged into a release or backport branch does not count). The fallbacks are `git cherry` and a *cumulative-prefix* patch-id match (`git diff <merge-base> <k-th commit>` against every base commit), because a multi-commit ancestor squashed into one commit defeats per-commit `cherry`, and a squash whose context lines drifted defeats both. Only a *leading* run of such commits counts: `rebase --onto origin/<base> <last>` drops exactly that run, and a hotfix cherry-picked mid-branch is an ordinary conflict. An API error warns and falls through to the git signals; it never decides the result. No signal proves the change is *still* on the base (it may have been reverted), so the comment asks the author to check before dropping commits
  - **Four jobs, split by what may run where.** `resolve` runs the agent, whose `git add`/`git commit` execute hooks and filters it can write. `build` runs `build-command`, which is code from the PR. Both hold a read-only `GITHUB_TOKEN` and no push credential. `env -u` in the same step is not enough: the variable stays readable in `/proc/$PPID/environ`, and on ubuntu-latest the build has sudo and could replace `git` before a later step pushes. Only `publish` (slim) references `RELEASE_PLEASE_TOKEN` or pushes, and it runs no repository code. It pushes from a bare repository it `git init`s, after re-fetching the PR head and the base and requiring the exported commit to be exactly `merge(live PR head, a commit on the base)`. The jobs hand over a `report.json` and a git bundle as artifacts. `Read resolution report` (byte-identical in `build` and `publish`) validates the report field by field, rejects any key it does not know, and writes a *fixed* key list to `$GITHUB_OUTPUT`, because the job that wrote it ran the agent: emitting the report's own keys let an extra key carrying a newline append a second, winning `last_equivalent=`/`merge=` line after the checked one. A forged report or build result can at most push its own merge to its own PR branch. `find-conflicts` (slim, API only, no repository code) is the other job with a write-scoped token, declared explicitly: it comments on and closes stale automated PRs, so `resolve` needs no `contents: write`. All comments about a resolution come from `publish`
  - **Never pushed to: the default branch or a protected one.** `RELEASE_PLEASE_TOKEN` can often bypass branch protection, so a conflicting same-repo PR with `head=main` would get the base merged into `main` unreviewed. `find-conflicts` skips (with a `::notice::`) any PR whose head is the default branch (`gh api repos/$REPO --jq .default_branch`) or has `protected != false` (`repos/$REPO/branches/<@uri name>`, readable with `contents: read`), and `publish` asks both again right before `git push`. Failure is closed everywhere: an unreadable default branch fails `find-conflicts`, an unreadable protection skips the PR there and refuses the push in `publish`
  - **The agent holds no `git push`, no `gh` and no token; the agent writes, bash publishes once.** Its only directory outside the checkout is `$RUNNER_TEMP/auto-resolve-agent` (`--add-dir`), which holds nothing but the abort file it may write. Never `--add-dir "$RUNNER_TEMP"`: that tree holds the runner's file-command files (`GITHUB_ENV`, `GITHUB_PATH`), so `Write` there could set `BASH_ENV` or prepend a fake `git` for the check step. As a second layer the check step resets `PATH=/usr/bin:/bin`. `Check resolution` decides the outcome. It requires the commit's parents to be exactly `(pre_head, base_sha)` (both recorded before the agent runs), a git config unchanged since the merge step, a clean tree (untracked files included), and no `<<<<<<< `/`>>>>>>> ` line added to a conflicted file. `=======` is deliberately not matched, because setext headings use it legitimately. A failed agent *step* (API outage, expired token, turn limit) is `agent-error`: the run goes red with no PR comment and no marker, so the next run retries
  - **The prompt is a quoted heredoc with `@@NAME@@` placeholders that jq substitutes in one pass.** An unquoted heredoc would run the prompt's backticks. A `${{ }}` would put the attacker-controlled PR title into the script. Sequential `${var//…}` replacement lets a title inject a later placeholder, and with bash 5.2's `patsub_replacement` an `&` in an unquoted replacement expands to the matched text
  - **A GITHUB_TOKEN push starts no CI.** Without `RELEASE_PLEASE_TOKEN` the resolution is still pushed, but a `::warning` and the PR comment both say that no CI ran on that head. The comment also says whether `build-command` validated the merge. Do not add a permission (for example `statuses: write`) to gate this differently: a reusable workflow that requests more than the caller's job grants fails at startup in every consumer
  - **Every comment carries a hidden marker and is posted once.** The stacked notice is keyed on the PR head only, because the base moves on every push. An unresolved report (abort, unfinished merge, failed build, invalid merge) is keyed on the (head, base) pair, and the `prior` step skips the agent for a pair that already has one, except on `workflow_dispatch`. `.github/tests/auto-resolve-stacked/run.sh` (`just auto-resolve-fixtures`) extracts the shipped steps of all four jobs and runs them in sequence against real git fixtures. These include the incident (`cc -fsyntax-only` on a duplicated `static int`), a forged report and one with an injected extra key, heads on the default or a protected branch (and failing lookups), a fake `git`/`jq` on an injected `PATH`, hooks and a `pushInsteadOf` left in the resolve repository, a stub `gh`/`npx` and a hostile PR title. The `pushInsteadOf` base ends in `/` so that a rewritten push really lands in the trap repository; without the slash it went to a nonexistent path and the trap assertion could never fail
- **`reusable-enforce-conventional-commits.yml`** — auto-fixes PR titles to conventional commits format with 80+ verb-to-type mappings
- **`reusable-changelog-review.yml`** — scheduled upstream-changelog triage (Claude Code's changelog by default). Two-job shape: a pure-bash pre-check gate (version compare against a tracking JSON, skip-if-existing-open-issue idempotency, excerpt slicing, caller-supplied analyzer script) followed by one opus triage run that writes the tracking-issue body and state entry, and one bash step that publishes the issue and a single JSON-ratchet PR. The schedule lives in the caller (`workflow_call` cannot carry one); the repo-specific keyword→file mapping stays in the calling repo via the required `analyzer-script` input. Model/effort default to opus/medium via inputs

  Five things not to re-derive:
  - **The agent writes; a bash step publishes, once.** The triage agent writes `triage-issue-body.md` and `triage-entry.json` and holds no grant that files, commits, or pushes. `Publish tracking issue and ratchet PR` looks for an open issue with the exact title, creates one only if none exists, and never retries a failed create; it re-reads the listing instead. On github.com, `gh issue create --assignee` files the issue, then fails the separate `replaceActorsForAssignable` call and exits non-zero without printing the URL, so an agent that retried filed every tracking issue twice (claude-plugins #2656/#2657, #2711/#2712; claude-plugins#2720). Labels and assignee go through REST on `github.token` and are read back, because the assignees endpoint answers 201 while dropping a login it cannot assign; the state file records the read-back. `.github/tests/changelog-review-publish/run.sh` (`just changelog-publish`) runs the extracted step against a stub `gh`
  - **The tool list belongs in `claude_args: --allowedTools`, never in `additional_permissions:`.** That input takes a GitHub *permissions map* (`actions: read`); a Claude tool list there is silently inert, the action's default policy then denies `gh issue create` / `git push`, and **the SDK exits 0 on a permission denial** — so the workflow runs green and files nothing. It did exactly that for 13 consecutive weeks in claude-plugins. Diagnose from the job log's `SDK options:` block: `allowedTools` absent = broken. **Do not gate on `permission_denials_count > 0`** — a healthy run has one, from the deliberately un-granted `WebFetch`. The same inert list was also converted in `reusable-auto-fix.yml` and `reusable-claude-review.yml`; see **The `additional_permissions` trap** below
  - **Labels are provisioned by the gate job, before the triage run**, so the skip-if-exists lookup and the publish step's label call find them. The colour is a *quoted* string: bare `5319e7` is a YAML 1.2 float (`53190000000`) and `gh label create` answers HTTP 422. Create-if-missing rather than `--force`, so a shared label like `maintenance` is not recoloured weekly
  - **A backlog is windowed, not truncated** (`max-versions-per-run`, default 25 — the review-stall threshold the consumer's own analyzer enforces). The excerpt is newest-first, so the old byte cap kept the newest bytes and dropped the oldest versions *while still ratcheting to the top of the range*, skipping them for good. Windowing instead keeps the **oldest** N versions after `lastCheckedVersion` and ratchets only to the top of that window; the next run continues from there because upstream's latest still exceeds the new tracked version. Downstream consumers must use the `effective_latest` output, never `latest_version`
  - **Token usage comes from the action's `execution_file`, never from full output** (issue #54). The job log cannot show cache hits: with `show_full_output` off the action logs only duration, turns, cost and denials, and `sanitizeModelUsage` strips token counts on purpose. The action writes every SDK message to `$RUNNER_TEMP/claude-execution-output.json` whatever `show_full_output` says, and `Summarise triage token usage` reduces it to numbers: a per-call table and the cache hit rate in the job summary, plus a numbers-only `changelog-triage-usage` artifact (90 days). Never turn on `show_full_output` or `display_report` for this on a public workflow. Totals come from the result message's `modelUsage`, which covers every API call; per-call rows come from assistant messages, **grouped by `message.id` with the per-field max**, because the SDK emits one assistant message per content block and repeats the usage; the gap between the two is printed. The step runs after publish under `!cancelled()` with `continue-on-error`, so it reports on a max-turns failure and can never gate publication; the upload (SHA-pinned like every other new `uses:`; the harness asserts it) sets `overwrite: true` because "Re-run failed jobs" re-uploads the same name. `just changelog-usage` runs the extracted step against fixtures, hostile values included

#### The `additional_permissions` trap

`anthropics/claude-code-action`'s `additional_permissions:` input takes a **GitHub permissions map** — `actions: read` and nothing else. A Claude **tool list** written there is silently inert: no `allowedTools` reaches the SDK, the action's default policy denies the writes, and **the SDK exits 0 on a permission denial**, so the run goes green having done nothing. Three workflows here had it; `reusable-claude.yml` always had it right and is the canonical shape:

- tools go in an `allowed_tools` input (comma-separated), composed into `claude_args` as `--allowedTools "..."` — a **separate input from `claude_args`** on purpose, so a caller overriding `--model`/`--max-turns` cannot silently drop the tool grant. `reusable-changelog-review.yml` is the deliberate exception: its list is pinned inline and not caller-tunable, because the *exclusions* (`WebFetch`/`WebSearch`) are part of its prompt's contract that the pre-sliced excerpt is the only input
- `additional_allowed_tools` appends caller extras; `additional_permissions` is the permissions map only
- `--allowedTools` is **additive** over the action's defaults, so listing tools widens rather than restricts
- naming `TodoWrite` is a real grant, not decoration — since 2.1.233 the todo/task tools are off by default on current models and listing one is the session-wide opt-in
- diagnose from the job log's `SDK options:` block: `allowedTools` absent = broken

#### Claude-Powered Analysis Workflows

Security, quality, and accessibility workflows use `anthropics/claude-code-action@v1`. Each exposes `max-turns` (default 50) and `model` inputs — opus for deep-reasoning jobs, sonnet for the more mechanical ones:
- **Security**: `reusable-security-{secrets,deps}.yml` (sonnet), `reusable-security-owasp.yml` (opus)
- **Quality**: `reusable-quality-{code-smell,typescript}.yml` (sonnet), `reusable-quality-async.yml` (opus)
- **Accessibility**: `reusable-a11y-aria.yml` (sonnet), `reusable-a11y-wcag.yml` (opus)

All require `CLAUDE_CODE_OAUTH_TOKEN` secret. They analyze changed files in PRs and publish findings to the **job summary and PR file annotations** — never a PR comment. The action grants no comment tool, so a prompt asking Claude to comment only produced denials and discarded the findings (issue #47); `$GITHUB_STEP_SUMMARY` and `::warning`/`::error` both work under the `contents: read` these jobs already hold, and need nothing in `additional_permissions:`.

Seven things not to re-derive:
- **The publish block is byte-identical across all eight**, bar four env values (`TITLE`, `BLOCKING_SEVERITIES`, `COUNT_KEYS`, `NOTHING_SCANNED_REASON` — masked in the drift check, so a per-workflow message stays possible without forking the block). It is duplicated on purpose: `uses:` takes no expressions, so a shared composite action would execute at floating `@main` even for a consumer who pinned this repo by SHA, and a script under `.github/` is not checked out either (these jobs run `actions/checkout` with no `repository:`, so the workspace is the *caller's*). `scripts/check-publish-drift.sh` (`just publish-drift`) enforces the identity and fails on absence as well as drift.
- **Every gate predicate compares numerically** (`steps.publish.outputs.blocking > 0`), never as a string (`!= '0'`), and none carries `always()`. GitHub coerces the empty string a skipped publish step leaves behind to 0 for `>`, so a numeric gate cannot fire on a PR that scanned nothing; string comparison does the opposite and would take every consumer red on a README-only PR.
- **The fixture harness EXTRACTS the shipped block** out of a workflow with `awk`/`sed` rather than holding a retyped copy (`just publish-fixtures`). That is what caught the annotation-escaping, non-object-element and `index()`-scope defects; a retyped copy is not the code under test.
- **Everything the model emits is untrusted at the shell boundary**, `--json-schema` notwithstanding: the `enum` on `severity` and the `integer` on the counts are requests to the model, not constraints the runner applies. So annotation payloads (`severity` included) are `%`/CR/LF-escaped; `line` and the counts are type-checked, since a count carrying a newline writes a second `key=value` line into `$GITHUB_OUTPUT` and can overwrite `blocking`; and `findings` is shape-checked in the guard, because a non-array aborts jq under `set -e` and discards summary, annotations and outputs together.
- **The payload is read from `execution_file`, never from `structured_output` through env.** The publish block binds `EXECUTION_FILE: ${{ steps.analyze.outputs.execution_file }}` (the action's transcript at `$RUNNER_TEMP/claude-execution-output.json`, a JSON array of SDK messages) and extracts `[.[] | objects | select(.type == "result")] | last | .structured_output` into a file that every jq call reads. An env string of 131072 bytes or more (`MAX_ARG_STRLEN`) fails the execve of the step's own shell with E2BIG before line 1 runs, so a large scan published nothing, not even the degrade message (#61); passing it to jq via `--arg`/`--argjson` only moves that failure one exec later, and interpolating it into `run:` is the #57 injection. The fixtures obey the same rule: payloads reach jq on stdin and `env_under_cap()` refuses any over-cap export. Reading the transcript also recovers findings the env output never carried, since upstream sets `structured_output` only on a clean success: a result flagged `is_error` or one over `--max-turns` publishes with the "may be incomplete" warning, while an `error_*` result normally carries none and degrades. This is a contract with the floating `claude-code-action@v1` (its `execution_file` output and the array-of-messages shape, verified at cab360f), so an unset, missing, unparseable or reshaped file degrades loudly with zeroed counts rather than crashing the step. The degrade branch also writes `degraded=true` (only the success path writes `false`), and that is what keeps the read from failing *open*: under `--json-schema` an analyze outcome of `success` means the action had a `structured_output`, so a success that publish could not read lost a real report on this side, and its zeroed counts would skip every severity gate — `Classify analysis outcome` therefore fails any `success` run whose `degraded` is not exactly `false`
- **A missing `structured_output` is a warning, every other analysis failure is red.** With `--json-schema` the action fails the step whenever a `subtype: success` run returns no `structured_output`, and that happens at random on an unchanged SHA. So the `analyze` step is `continue-on-error: true`, and `Classify analysis outcome` (after the END marker, outside the drift-checked block, and before any severity gate, since its exit 1 is now what skips them) reads the last `result` message in `execution_file`: `success` + `!is_error` + no `structured_output` → `::warning`, job green; anything else → `::error` with the reason, job red. On an analyze outcome of `success` it reads no transcript and instead fails closed on the publish step's `degraded` output (above), so the green warning path is reserved for a run where Claude returned no `structured_output`, never for a scan whose output the workflow failed to read. `read` collapses an empty `@tsv` field (tab is IFS whitespace), which is why the `word` helper maps empty to `unknown`. Consequence for callers: on the warning path the job result is `success` **and every count output is `0`** (the publish block's degrade branch writes zeroed counts), so neither `result` nor a zero count means the scan ran clean — a gate like `result == 'success' && secrets-found == '0'` passes a PR that was never analysed. Only the `::warning` annotation and the job summary tell the two apart. `.github/tests/analysis-verdict/run.sh` (`just analysis-verdict`) extracts the shipped step body and runs it against fixture execution files, runs the shipped publish step on the warning path to pin the zeroed counts, chains shipped publish into shipped verdict on a `success` outcome with an unset, empty, reshaped or result-less execution file to pin the fail-closed path, and asserts the body is identical across every `--json-schema` workflow; `.github/tests/analysis-contract/run.sh` (`just analysis-contract`) pins the schema, prompt and gates.
- **push is refused, not scanned.** claude-code-action v1 throws `Unsupported event type` for any event outside the `switch` in its `src/github/context.ts` (issues, issue_comment, pull_request, pull_request_target, pull_request_review, pull_request_review_comment, workflow_dispatch, repository_dispatch, schedule, workflow_run), so a caller with a `push` trigger got a red check that read like a leak (issue #63, comfyui-nodes#162). The first step, `Check trigger is supported` (id `event`, no `if:`), matches that list and writes `supported` / `unsupported`; checkout, the file list, security-deps' setup and audit steps, and `analyze` all compare `supported == 'true'`, a string equality, so an unset output fails closed — never `!= 'false'`. The shared `Report that nothing was scanned` step then names the refused trigger through `UNSUPPORTED_EVENT`, so the job is green with one notice. Only `pull_request` yields a meaningful range: the `HEAD~1` branch stays because workflow_dispatch and schedule reach it (deleting it, the issue's option 1, would break them), and the other allowlisted events also land there and scan the default-branch tip. `pull_request_target` deliberately stays on that path: checkout has no `ref:`, so it diffs the base, and checking out the PR head in a job holding `CLAUDE_CODE_OAUTH_TOKEN` and `id-token: write` is a pwn-request. The list is a copy of floating `@v1`'s: if upstream adds `push`, the guard keeps refusing it green until the list is updated. `.github/tests/event-guard/run.sh` (`just event-guard-fixtures`) extracts the step and checks the wiring; the report text is in `just publish-fixtures`.

### OpenCode-Powered Workflows

- **`reusable-opencode.yml`** — enables `/opencode` (or `/oc`) mentions in issue comments and PR review comments, via `anomalyco/opencode/github`. Requires the `OPENCODE_API_KEY` secret (pushed by gitops to repos flagged `opencode = true`).

  **There is no automatic-review mode, by construction.** The action's `github/index.ts` opens with `assertContextEvent("issue_comment", "pull_request_review_comment")` and throws `Unsupported event type` on anything else, then throws again unless the body matches `/(?:^|\s)(?:\/opencode|\/oc)(?=$|\s)/`. A `pull_request`-triggered caller therefore cannot work — the only route to automatic review is a shim that posts a `/oc` comment on PR open, which needs a PAT or App token (comments made with `GITHUB_TOKEN` do not trigger workflows).

  Two details worth not re-deriving:
  - The job's `if:` is a deliberately loose `contains()` pre-filter; a **guard step** then applies the action's exact regex and skips the action when the mention is only a substring (`/october`). Without it, such a comment spins a runner and fails red on the action's own throw. The comment body reaches the guard via `env:`, never interpolated into the script — it is attacker-controlled.
  - The action is pinned to a release SHA, but **pinning does not fully close the floating-version exposure**: `action.yml`'s first step `curl`s the *latest* opencode CLI release at runtime regardless of the pin. The pin covers the wrapper, not the binary it installs. Fix proposed upstream in [anomalyco/opencode#39147](https://github.com/anomalyco/opencode/pull/39147) — runs the installer bundled at the pinned ref and adds a `version` input passed to the installer. **That PR was auto-closed on 2026-08-28 and the caveat is therefore open-ended, not pending.** It was closed by upstream's PR-cleanup bot on its stated criteria — older than a month, fewer than two positive reactions (the PR has zero) — not on review; a reopen request the same day is unanswered. The branch `fix/pin-installer-and-cli-version` is intact and the linked issue [#39163](https://github.com/anomalyco/opencode/issues/39163) is still open, so closing the gap means getting the PR reopened (reactions are the bot's own criterion) or refiling it. Re-verified against upstream HEAD on 2026-09-12: `github/action.yml` still resolves `releases/latest` and pipes `https://opencode.ai/install` to bash, and `github/index.ts:128` still carries the `assertContextEvent` that makes the mention-only constraint above structural.

  Auth defaults to the OpenCode App OIDC exchange (`id-token: write`), which needs the [opencode-agent App](https://github.com/apps/opencode-agent) installed on the calling repo; set `use_github_token: true` to use `GITHUB_TOKEN` instead. Note the action requires the commenting actor to hold **write or admin** permission, so outside contributors cannot drive it.

## Conventions

- **Commit messages**: [Conventional Commits](https://www.conventionalcommits.org/) — `type(scope): description`
- **Action pinning**: actions are pinned to full SHA with version comment (e.g., `actions/checkout@<sha> # v6.0.2`)
- **Concurrency groups**: workflows use concurrency groups to prevent racing (e.g., `release-please-${{ github.repository }}`)
- **Secret fallbacks**: workflows use `${{ secrets.CUSTOM_PAT || secrets.GITHUB_TOKEN }}` pattern for optional PATs
- **Permissions**: each workflow declares minimal `permissions` at workflow level
