# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

This is the **laurigates/.github** repository — a special GitHub repo that provides default community health files and reusable GitHub Actions workflows for all [@laurigates](https://github.com/laurigates) repositories. It contains no application code or build system; its own workflow tests live under `.github/tests/` (see [Testing](#testing)).

## Repository Structure

- **Root files** (`CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`, `SUPPORT.md`) — default community health files inherited by all laurigates repos unless overridden
- **`profile/README.md`** — GitHub profile page content
- **`.github/ISSUE_TEMPLATE/`** — default issue templates (bug report, feature request)
- **`.github/PULL_REQUEST_TEMPLATE.md`** — default PR template
- **`.github/workflows/reusable-*.yml`** — reusable workflows (the main deliverable of this repo)

## Workflow Architecture

All workflows are **reusable** (`workflow_call`) and called from other repos via:
```yaml
uses: laurigates/.github/.github/workflows/reusable-<name>.yml@main
```

### Runner selection: `ubuntu-slim` for API-only jobs

Jobs whose entire body is GitHub-API churn — `gh` calls, `actions/github-script`,
`create-github-app-token`, release-please, label/PR bookkeeping — run on
**`ubuntu-slim`** (1 CPU, $0.002/min vs $0.006/min). Everything else stays on
`ubuntu-latest`.

`ubuntu-slim` is an *unprivileged container*, not a VM, and carries no hosted
tool cache. It therefore **cannot** run:

- anything needing a Docker daemon — including actions that only *look* like
  plain composites: `renovatebot/github-action`, `trufflesecurity/trufflehog`,
  `pypa/gh-action-pypi-publish` (`gitleaks/gitleaks-action` is `node24`, so it
  is fine)
- `container:` / `services:` jobs, `sudo`/`apt-get`, mounts, kernel features
- Go, Rust, Java/Gradle/Maven, .NET, Ruby, PHP, Swift, Android, browsers,
  databases, kubectl/helm, CMake/Bazel, CodeQL — none are preinstalled

Preinstalled and safe to rely on: bash, Node 24, Python 3.12, gcc/g++, git+LFS,
`gh`, jq, yq, curl, zstd, AWS/Azure/gcloud CLI. `actions/setup-node` /
`setup-python` still work but must *download* the runtime (no tool cache), so
prefer slim for jobs that don't need one.

When a job in a reusable workflow is split (a cheap gate + an expensive Claude
step), put only the gate on slim — see `reusable-changelog-review.yml` and
`reusable-auto-resolve-conflicts.yml`.

### Container Build/Release (build-once/promote pattern)

The container workflows implement a two-phase pattern:

1. **`reusable-container-build.yml`** (PR phase) — builds and pushes a `:next-{version}` pre-release image to GHCR during the release-please PR
2. **`reusable-container-release.yml`** (tag phase) — resolves a single release *candidate* (promoted `:next-{version}` digest, or a rebuild), scans it, and only then creates the release tags. Optional cosign keyless signing via Sigstore

The version is extracted from the version file (default: `package.json`) during build, and from the git tag (stripping `tag-prefix`) during release. The release tags derive from that stripped version alone, so a `tag-prefix` that does not prefix the release tag fails the run. `.github/tests/container-release-tags/run.sh` (`just container-release-tags`) pins this.

#### The vulnerability scan is a publication gate, not a report

The release job's invariant: **exactly one step creates a release tag, it has no `if:`, and the step immediately before it is the scan.** The scan's subject is a digest resolved by a step that also has no `if:` and hard-fails when it cannot resolve one, so both the promote and the rebuild path are covered by construction rather than by a condition someone can get wrong.

Five things not to re-derive:

- **The rebuild path pushes to `:next-{version}`, never to `meta.outputs.tags`.** Pushing the release tags from `docker/build-push-action` is what made the old scan unable to gate anything — the artifact was already published by the time it ran. Release tags are applied by `docker buildx imagetools create` from the scanned digest
- **The scan lives in `.github/actions/scan-image` and must be referenced fully-qualified** (`laurigates/.github/.github/actions/scan-image@main`). A `./`-relative `uses:` inside a reusable workflow resolves against the *caller's* checkout and fails in every consumer. It enumerates platform manifests from the image's own index, so a multi-arch caller's arm64 layers are scanned without anyone passing `platforms` twice
- **`--exit-code 13`, not `1`.** Trivy exits with the requested code for findings (`types.ExitError`) and `1` for everything else (`log.Fatal`), so `1` makes a DB-pull failure indistinguishable from a real CVE — and the natural response to the former is to switch the gate off. Confirmed on the pinned `v0.70.0` binary
- **The promote wait and the digest resolution are the same step, and the digest comes out of the wait's own probe.** `pr-image` waits for the PR-phase build (issue #51) and resolves `:next-{version}` to a digest in one place, which is the only read of that mutable tag in the job — freshness, the scan and publication all address the digest, so a concurrent PR-phase build moving the tag mid-job cannot change what ships. Editing the wait means preserving `PROBE_DIGEST`; editing the digest handling means preserving the bounded wait
- **`scan-enforcement` is a validated string (`block`|`warn`), not a boolean.** An unrecognised value is a hard error at the top of the job; `continue-on-error: ${{ inputs.scan-enforcement == 'warn' }}` then means anything that is not exactly `warn` blocks. `warn` publishes *and* fails the job, reproducing the pre-gate outcome rather than swallowing the failure into a green run

The PR-phase build's scan is **advisory by default** (`scan-mode: advisory|block|off`) and is not the gate: a CVE published against an unchanged base would otherwise block every unrelated release, and the rebuild path exists precisely when the PR image is not what ships. `scan-mode` is validated at the top of the build job for the same reason `scan-enforcement` is — its `continue-on-error: ${{ inputs.scan-mode != 'block' }}` fails *open*, so an unvalidated `blocking`/`enforce`/`true` would silently downgrade a caller's blocking check to advisory.

#### What a blocked release looks like in a consumer

Read from laurigates/pal-mcp-server's tag-push runs (issue #62). Between v11.0.0 and v11.9.0 the gate blocked 8 of 12 releases, on the promote path (v11.9.0, `Total: 4 (HIGH: 4, CRITICAL: 0)`) and on the rebuild path (v11.8.1, `Total: 11 (HIGH: 8, CRITICAL: 3)`). Three things follow for a caller:

- **A block leaves the git tag and the GitHub Release in place with no image.** `:next-{version}` is the only reference to that build, and `latest` stays on the last release that passed. The job summary's `Publication: BLOCKED` line renders, because the scan step still writes `result=findings` before it fails
- **Re-running the job cannot clear it.** The re-run scans the image built from the same tag, which carries the same lockfile. The fix is a refreshed lockfile or base image on the default branch and a new patch release
- **The fix often lands under a hidden commit type.** A Renovate lock refresh is `chore(deps)`, which opens no release PR, so the clean lock stays unpublished until the next `feat` or `fix`. pal-mcp-server cut 11.8.2 and 11.9.1 with a `Release-As:` footer for this reason (`.rulesync/rules/commit-and-release.md`)

The release PR's `build / build` job scans `:next-{version}` before the merge, and its log shows the result. That scan covers the same image the tag run promotes when the build context is unchanged. A lockfile audit on every PR (pip-audit, or `reusable-security-deps.yml`'s osv-scanner job) reports the finding earlier still.

### Release Automation

- **`reusable-release-please.yml`** — wraps `googleapis/release-please-action`, requires a PAT (`MY_RELEASE_PLEASE_TOKEN`) since GITHUB_TOKEN can't trigger downstream workflows. Carries a **missed-release guard**: when the action reports neither `prs_created` nor `releases_created`, a follow-up step compares `github.event.before...github.sha` via the GitHub compare API and annotates (or fails, per `missed-release-check`) if the range held commits matching `releasable-types`. This exists because release-please's conventional-commit parser can throw on a squash body — repos with `squash_merge_commit_message = PR_BODY` inherit the PR description as the commit body, and a fenced code block there discards *every* commit in the range while the run stays green (issue #40). The guard only catches the all-or-nothing case; the root-cause fix is per-repo `squash_merge_commit_message = COMMIT_MESSAGES` in gitops

  Also **assigns the release PR** (`pr-assignees`, defaulting to `github.repository_owner`). release-please has no native assignee config, and its PRs are bot-authored and mention no one, so they match none of GitHub's dashboard/mobile feeds — not `author:@me`, not `review-requested:@me`, not even `involves:@me`; an assignee is the only thing that files them under a human. Two things not to re-derive: **`@me` is unusable** — `gh` resolves it to the *token* owner, which is the App bot whenever `app-id` is set — and the step must run *before* the missed-release guard, since `missed-release-check: error` would otherwise skip it. It reads `steps.release.outputs.prs` (set on create *and* update, one entry per package in manifest mode) and falls back to listing open `release-please--branches--*` PRs when that output is empty, so an already-open PR still gets assigned. Assign failures warn rather than fail the release. Set `pr-assignees: none` to opt out — `''` cannot be the opt-out because it means "fall back to the owner"
- **`reusable-fix-release-conflicts.yml`** — detects conflicted release-please PRs, closes them, deletes the branch, and retriggers release-please to recreate cleanly. Pass `app-id` + `APP_PRIVATE_KEY` to use an App token instead of `RELEASE_PLEASE_TOKEN || GITHUB_TOKEN`. The token used (App or PAT) needs `actions: write` as well as contents and pull-requests write, because the workflow's `permissions:` block covers only `GITHUB_TOKEN`; without it the job closes the PR and deletes the branch, then fails on the `gh workflow run` dispatch, and nothing recreates the release PR until the next push to main (issue #114)
- **`reusable-clear-autorelease-labels.yml`** — manual escape hatch (`workflow_dispatch` caller) that strips a stale `autorelease: pending` label from closed PRs. When the release/tag step fails, the merged release PR keeps the `pending` label and every subsequent run re-attempts the same failed release; clearing it lets release-please move on. Supports a `dry_run` input
- **`reusable-auto-merge-image-updater.yml`** — creates, approves, and auto-merges ArgoCD Image Updater PRs in a single job (workaround for GITHUB_TOKEN anti-recursion)

### Claude-Powered Workflows

- **`reusable-claude.yml`** — enables `@claude` mentions in issues and PRs. Supports configurable runner, max turns, and system prompt for CI turn budget awareness. Posts continuation comments on max-turns exhaustion. When the event concerns a PR (`issue_comment` on one, `pull_request_review`, `pull_request_review_comment`) it applies the same `skip_authors` / `skip_paths` gate as `reusable-claude-review.yml` below, reading the author from `github.event.pull_request.user.login || github.event.issue.user.login`; an `@claude` on a plain issue is never skipped. A caller that wants `@claude` to work on claude-config-sync PRs sets `skip_authors: ''`. Its pushes arrive as `github-actions[bot]`, not `claude[bot]`: checkout@v6 keeps `GITHUB_TOKEN` as an extraheader in an `includeIf` file that claude-code-action's cleanup does not scan (anthropics/claude-code-action#1721), and that header outranks the App token. The pushed head's runs are held for approval, and the analysis workflows default `allowed-bots` to `claude[bot],claude,github-actions[bot]` so they do not refuse them. Do not fix this with `persist-credentials: false`: tag mode fetches before it configures git auth, so every mention fails on a private repo (anthropics/claude-code-action#1711)
  - `Detect failure type` reads only the action's execution file, bound through `env:`, and the continuation comment reads every value from `process.env`; `structured_output` is deliberately unused, because upstream sets it only on success and it is the caller's `--json-schema` object, not an SDK result (issue #78). `just claude-failure-type` runs both extracted steps against hostile execution files and fails on any `${{` in a script body of the job
- **`reusable-claude-review.yml`** — automated PR review using Claude Code. Skips release-please PRs and bot actors by default
  - **Cost guard (laurigates/gitops#341).** A `gate` step runs before checkout and skips green with a `::notice` when the PR **author** (`github.event.pull_request.user.login`, not the actor) is in `skip_authors` (default `laurigates-claude-config-sync[bot]`), or when every changed file, and the previous path of every renamed one, matches `skip_paths` (default `.claude/**` and `.mcp.json`; bash patterns, `*` crosses `/`; root-anchored, so `pkg/.mcp.json` does not match). Both inputs take comma- or newline-separated lists, and `''` disables either check. The files come from `gh api --paginate repos/$REPO/pulls/$PR/files` under the `pull-requests` scope the workflow already holds; a list of 3000 files (the API's cap) or of none never skips, and a failed read fails the step. Checkout and the Claude step require `steps.gate.outputs.run == 'true'`. The author check is what stops a human's reopen of, or push to, the claude-config-sync PR from starting a review; the job-level `if:` still compares only the actor. The step's `run:` body is byte-identical in `reusable-claude.yml`, and `.github/tests/claude-cost-guard/run.sh` extracts and runs both
  - **Evidence rules (ForumViriumHelsinki/.github#199).** The default `prompt` here and `reusable-claude.yml`'s `--system-prompt` carry the same rules: a blocker or a "fails / does not parse / does not exist" claim cites a file read, tool output or CI result from the run, otherwise it is posted as a question; syntax and lint verdicts come from CI via the `github_ci` tools, never from reading code; and (in `reusable-claude.yml`, which allows `Bash(python *)`) a local interpreter counts only at the repo's declared version, since the Ubuntu 24.04 runners' Python 3.12 rejects valid 3.14 syntax (PEP 758 `except A, B:`). A caller's `review_prompt` replaces them. The action parses `claude_args` with shell-quote, which expands `$NAME` inside double quotes to nothing, so the system prompt holds no `$` or backtick. `.github/tests/claude-evidence-rule/run.sh` checks every tag-mode claude-code-action step for the rules and that `$`/backtick rule, and fails if a `track_progress` review job's default `allowed_tools` grants an interpreter or test runner, which would run PR-controlled code in a job holding `pull-requests: write`
- **`reusable-auto-fix.yml`** — analyzes failed CI workflows and either auto-fixes (commit + push) or opens a GitHub issue. Includes recent-fix detection to prevent loops. The agent pushes with the checkout's credential: an App token when `app-id` + `APP_PRIVATE_KEY` are passed, else `PAT_TOKEN`, else `GITHUB_TOKEN`, whose push starts no CI (the PR's runs are held and later concluded `failure` with zero jobs, so mcu-tinkering-lab#749 merged an unverified fix). An App or PAT that bypasses branch protection lets the agent push past it too. Its tool list was inert (see the trap below), which silently disabled the commit/push and issue-creation the workflow exists for; it also never forwarded `actions: read`, so Claude could not read CI results either

  **Author gate (laurigates/gitops#341, issue #119).** The job's first step, `Check PR author` (id `gate`), skips green with a `::notice` when the failed branch's PR author is in `skip_authors` (default `laurigates-claude-config-sync[bot]`, same input shape as `reusable-claude-review.yml`; `''` disables it). It runs before the App token and checkout, so a skipped run mints no token and never checks out the branch, and every later step requires `steps.gate.outputs.run == 'true'`. It has to be a step: the job `if:` compares only the actor, and the `workflow_run` payload's `pull_requests[]` has no `user`. The PR comes from `pr_number`, else `gh pr list --repo --head <branch>`; no PR means it runs. The author is read with `gh api repos/$REPO/pulls/<n> --jq .user.login`, because that returns the `[bot]` login skip_authors uses (`gh pr view` reports an App as `app/<slug>`). A failed read fails the step. `.github/tests/claude-cost-guard/run.sh` extracts and runs the body

  **One failure, one issue.** Before the agent runs, a bash + jq step hashes the failure's most specific log line into a 12-hex signature (a failing pre-commit hook, else the first failed job's own `##[error]`, exception or failed step, never a later summary job's), and the next step lists open issues for the hidden body marker `<!-- auto-fix-signature: <sig> -->`. A match gets a comment quoting the hashed line, and the prompt's `directive` output forbids a new issue; otherwise the directive has the agent end the new issue's body with the marker. Whenever the lookup's mode is not `create`, `--disallowedTools` also denies `gh issue create` and `gh issue new`. Without this, laurigates/dotfiles collected eight issues (#414-#429) for one broken `uses:` ref. Three things not to re-derive:
  - **The lookup reads the repository issue listing, not the search API.** `gh issue list` without `--search` queries GraphQL `repository.issues`, which shows an issue as soon as it exists; the search index lags creation, and duplicates here were filed minutes apart
  - **`max_auto_fix_prs` counts open issues with a well-formed marker and pauses issue creation only**, never the auto-fix. It used to count open PRs from `auto-fix/*` branches (`head:` is a prefix match), which this workflow never opens (it pushes to the failing branch), so it never fired
  - **`.github/tests/auto-fix-dedup/run.sh` extracts the shipped step bodies** and runs them against real `--log-failed` output (`just autofix-fixtures`); it also checks that every `steps.<id>.outputs.<key>` resolves, because a mistyped one evaluates to '' and silently turns dedup off. It also asserts that no `run:` body in the job contains `${{` and that `Gather failure context` binds `branch`, `run_id` and `pr_number` through `env:`, because a branch name is caller-controlled text (a fork author chooses it) and an inline expansion is script injection (issue #69). Add a fixture there when a new failure shape is mis-grouped
- **`reusable-auto-resolve-conflicts.yml`** — on each push to the base, merges the base into every conflicting PR and has Claude resolve the conflicts (`model`, default `claude-opus-5-5`; `effort`, default `medium`, `''` omits the flag). A conflicting `chore/claude-config-sync` PR is closed, not resolved, like `renovate/*` and `dependabot/*`: it touches only Claude config and the claude-config-sync reconciler recreates it from the base on its next run (laurigates/gitops#341). Set `skip-release-please: true` in a repo that also calls `reusable-fix-release-conflicts.yml`: both run on push to main, and this one closes a conflicting release-please PR without retriggering release-please, so if it gets there first nothing recreates the PR. On laurigates/mcu-tinkering-lab it resolved a PR stacked on an already squash-merged PR by keeping both copies of the same change. The result defined a static variable twice, the agent pushed it itself, and no CI ran on the new head (issue #76). Seven things not to re-derive:
  - **A stacked-after-squash PR is detected before the merge, then commented on and never merged.** The primary signal is GitHub's commit→PR association: a branch commit that belongs to another PR with `merged_at` set *and `base.ref` equal to this PR's base* (a PR merged into a release or backport branch does not count). The fallbacks are `git cherry` and a *cumulative-prefix* patch-id match (`git diff <merge-base> <k-th commit>` against every base commit), because a multi-commit ancestor squashed into one commit defeats per-commit `cherry`, and a squash whose context lines drifted defeats both. Only a *leading* run of such commits counts: `rebase --onto origin/<base> <last>` drops exactly that run, and a hotfix cherry-picked mid-branch is an ordinary conflict. An API error warns and falls through to the git signals; it never decides the result. No signal proves the change is *still* on the base (it may have been reverted), so the comment asks the author to check before dropping commits
  - **Four jobs, split by what may run where.** `resolve` runs the agent, whose `git add`/`git commit` execute hooks and filters it can write. `build` runs `build-command`, which is code from the PR. Both hold a read-only `GITHUB_TOKEN` and no push credential. `env -u` in the same step is not enough: the variable stays readable in `/proc/$PPID/environ`, and on ubuntu-latest the build has sudo and could replace `git` before a later step pushes. Only `publish` (slim) references `RELEASE_PLEASE_TOKEN` or mints the App token (`app-id` + `APP_PRIVATE_KEY`), only it pushes, and it runs no repository code. It pushes from a bare repository it `git init`s, after re-fetching the PR head and the base and requiring the exported commit to be exactly `merge(live PR head, a commit on the base)`. The jobs hand over a `report.json` and a git bundle as artifacts. `Read resolution report` (byte-identical in `build` and `publish`) validates the report field by field, rejects any key it does not know, and writes a *fixed* key list to `$GITHUB_OUTPUT`, because the job that wrote it ran the agent: emitting the report's own keys let an extra key carrying a newline append a second, winning `last_equivalent=`/`merge=` line after the checked one. A forged report or build result can at most push its own merge to its own PR branch. `find-conflicts` (slim, API only, no repository code) is the other job with a write-scoped token, declared explicitly: it comments on and closes stale automated PRs, so `resolve` needs no `contents: write`. All comments about a resolution come from `publish`
  - **Never pushed to: the default branch or a protected one.** `RELEASE_PLEASE_TOKEN` can often bypass branch protection, so a conflicting same-repo PR with `head=main` would get the base merged into `main` unreviewed. `find-conflicts` skips (with a `::notice::`) any PR whose head is the default branch (`gh api repos/$REPO --jq .default_branch`) or has `protected != false` (`repos/$REPO/branches/<@uri name>`, readable with `contents: read`), and `publish` asks both again right before `git push`. Failure is closed everywhere: an unreadable default branch fails `find-conflicts`, an unreadable protection skips the PR there and refuses the push in `publish`
  - **The agent holds no `git push`, no `gh` and no token; the agent writes, bash publishes once.** Its only directory outside the checkout is `$RUNNER_TEMP/auto-resolve-agent` (`--add-dir`), which holds nothing but the abort file it may write. Never `--add-dir "$RUNNER_TEMP"`: that tree holds the runner's file-command files (`GITHUB_ENV`, `GITHUB_PATH`), so `Write` there could set `BASH_ENV` or prepend a fake `git` for the check step. As a second layer the check step resets `PATH=/usr/bin:/bin`. `Check resolution` decides the outcome. It requires the commit's parents to be exactly `(pre_head, base_sha)` (both recorded before the agent runs), a git config unchanged since the merge step, a clean tree (untracked files included), and no `<<<<<<< `/`>>>>>>> ` line added to a conflicted file. `=======` is deliberately not matched, because setext headings use it legitimately. A failed agent *step* (API outage, expired token, turn limit) is `agent-error`: the run goes red with no PR comment and no marker, so the next run retries
  - **The prompt is a quoted heredoc with `@@NAME@@` placeholders that jq substitutes in one pass.** An unquoted heredoc would run the prompt's backticks. A `${{ }}` would put the attacker-controlled PR title into the script. Sequential `${var//…}` replacement lets a title inject a later placeholder, and with bash 5.2's `patsub_replacement` an `&` in an unquoted replacement expands to the matched text
  - **A GITHUB_TOKEN push starts no CI.** Push precedence is App token, then `RELEASE_PLEASE_TOKEN`, then `GITHUB_TOKEN`; the first two trigger CI. With neither the resolution is still pushed, but a `::warning` and the PR comment both say that no CI ran on that head. The comment also says whether `build-command` validated the merge. Do not add a permission (for example `statuses: write`) to gate this differently: a reusable workflow that requests more than the caller's job grants fails at startup in every consumer
  - **Every comment carries a hidden marker and is posted once.** The stacked notice is keyed on the PR head only, because the base moves on every push. An unresolved report (abort, unfinished merge, failed build, invalid merge) is keyed on the (head, base) pair, and the `prior` step skips the agent for a pair that already has one, except on `workflow_dispatch`. `.github/tests/auto-resolve-stacked/run.sh` (`just auto-resolve-fixtures`) extracts the shipped steps of all four jobs and runs them in sequence against real git fixtures. These include the incident (`cc -fsyntax-only` on a duplicated `static int`), a forged report and one with an injected extra key, heads on the default or a protected branch (and failing lookups), a fake `git`/`jq` on an injected `PATH`, hooks and a `pushInsteadOf` left in the resolve repository, a stub `gh`/`npx` and a hostile PR title. The `pushInsteadOf` base ends in `/` so that a rewritten push really lands in the trap repository; without the slash it went to a nonexistent path and the trap assertion could never fail
- **`reusable-enforce-conventional-commits.yml`** — auto-fixes PR titles to conventional commits format with 80+ verb-to-type mappings. Opt-in `squash-message-check: off|warn|error` (default `off`), only for repos with `squash_merge_commit_message = PR_BODY`, adds a second job that parses the squash commit with release-please's own parser before merge. Three things not to re-derive:
  - **The title comes from the API, not the event payload.** The job runs `needs: fix-pr-title` (with `!cancelled()` in its `if:`, so a title the fixer cannot repair does not skip the body check) on ubuntu-slim and reads title and body with `gh api repos/$REPO/pulls/$N`: the fixer's `GITHUB_TOKEN` edit starts no new run, so the payload can still hold the old title. `jq -c` keeps the JSON on one line, so no title or body can forge a `GITHUB_OUTPUT` line
  - **The check lives in `.github/actions/squash-message-check`, referenced fully qualified** (`laurigates/.github/.github/actions/squash-message-check@main`), like `scan-image`. The action npm-installs `@conventional-commits/parser` alone into `$RUNNER_TEMP` and runs `check.mjs`, which rebuilds the squash message with GitHub's wrap model: `<title> (#N)`, then the body hard-wrapped at 72 code points, lines under a column-0 fence left alone, wrapped lines losing their indentation. The wrap, not the description as written, is what puts a mid-sentence call such as `name(` at a line start, where the parser reads a footer and throws. The parser stops at its first error, so when the title alone does not parse `check.mjs` parses the description again under a placeholder title (same line numbers, since the subject is one line); the job passes `title-reported: needs.fix-pr-title.result == 'failure'`, which turns the title error into a notice instead of a second failure
  - **`PARSER_VERSION` follows the release-please-action pin.** `googleapis/release-please-action@v4.4.1` in `reusable-release-please.yml` resolves release-please 17.3.0, which bundles parser 0.4.1; bump them together

  `.github/tests/squash-message-check/run.sh` runs the action's shipped install and parse steps against fixture bodies, plus the job's validate and PR-read steps against a stub `gh`, and fails when the two pins drift. It needs node, npm and npm registry access
- **`reusable-merge-method.yml`** — posts a `merge-method` check run whose title names the merge button to press ("→ Rebase and merge (…)" / "→ Squash and merge (…)"), and keeps one bot-applied `merge:rebase` / `merge:squash` label on the PR. The decision is `git-plugin/scripts/pr-merge-method.py` from laurigates/claude-plugins at the commit pinned in the `plugins-ref` input. The same script backs the git-plugin `gh pr merge` hook, and its rule table is `git-plugin/skills/github-pr-title/merge-strategies.md`. Four things not to re-derive:
  - **Never required.** GitHub gives a check no way to know which method the merge will use, and the merge-button default (`viewerDefaultMergeMethod`) is per user and read-only, so the check can only advise. A required check would also break the gitops rule against requiring reusable-workflow callers
  - **A human label is an override, the bot label is not.** The script reads the latest `labeled` event's actor for each `merge:*` label; under an override the workflow keeps the human label and removes the opposite one, so the PR never shows both. Writes made with `GITHUB_TOKEN` start no workflow, so the caller's `labeled`/`unlabeled` triggers fire only on human changes and the workflow cannot loop on its own label
  - **The labels come from laurigates/gitops `labels.tf`.** The workflow never creates them; a repo without them still gets the check run, plus a `::warning::`
  - **Body lint appears only where the body lands.** The script lints the PR body only for a squash, of a human PR, on a repo whose `squash_merge_commit_message` is `PR_BODY`. gitops sets `COMMIT_MESSAGES` on release-please repos until laurigates/gitops#318

  `.github/tests/merge-method/run.sh` runs the extracted publish step against a stub `gh` (`just test merge-method`)
- **`reusable-changelog-review.yml`** — scheduled upstream-changelog triage (Claude Code's changelog by default). Two-job shape: a pure-bash pre-check gate (version compare against a tracking JSON, skip-if-existing-open-issue idempotency, excerpt slicing, caller-supplied analyzer script) followed by one opus triage run that writes the tracking-issue body and state entry, and one bash step that publishes the issue and a single JSON-ratchet PR. The schedule lives in the caller (`workflow_call` cannot carry one); the repo-specific keyword→file mapping stays in the calling repo via the required `analyzer-script` input. Model/effort default to opus/medium via inputs

  Five things not to re-derive:
  - **The agent writes; a bash step publishes, once.** The triage agent writes `triage-issue-body.md` and `triage-entry.json` and holds no grant that files, commits, or pushes. `Publish tracking issue and ratchet PR` looks for an open issue with the exact title, creates one only if none exists, and never retries a failed create; it re-reads the listing instead. On github.com, `gh issue create --assignee` files the issue, then fails the separate `replaceActorsForAssignable` call and exits non-zero without printing the URL, so an agent that retried filed every tracking issue twice (claude-plugins #2656/#2657, #2711/#2712; claude-plugins#2720). Labels and assignee go through REST on `github.token` and are read back, because the assignees endpoint answers 201 while dropping a login it cannot assign; the state file records the read-back. The step also appends the body's `## Processing` section (processed by the repository owner; completed when every listed action is applied, filed or dismissed; closed by hand), matching the `changelog-review` row of claude-plugins `docs/issue-lifecycle.md` (claude-plugins#3346). It is written by bash, not asked of the agent, and a Processing section the agent writes anyway is dropped. `.github/tests/changelog-review-publish/run.sh` (`just changelog-publish`) runs the extracted step against a stub `gh` and reads the body the stub was handed
  - **The tool list belongs in `claude_args: --allowedTools`, never in `additional_permissions:`.** That input takes a GitHub *permissions map* (`actions: read`); a Claude tool list there is silently inert, the action's default policy then denies `gh issue create` / `git push`, and **the SDK exits 0 on a permission denial** — so the workflow runs green and files nothing. It did exactly that for 13 consecutive weeks in claude-plugins. Diagnose from the job log's `SDK options:` block: `allowedTools` absent = broken. **Do not gate on `permission_denials_count > 0`** — a healthy run has one, from the deliberately un-granted `WebFetch`. The same inert list was also converted in `reusable-auto-fix.yml` and `reusable-claude-review.yml`; see **The `additional_permissions` trap** below
  - **Labels are provisioned by the gate job, before the triage run**, so the skip-if-exists lookup and the publish step's label call find them. The colour is a *quoted* string: bare `5319e7` is a YAML 1.2 float (`53190000000`) and `gh label create` answers HTTP 422. Create-if-missing rather than `--force`, so a shared label like `maintenance` is not recoloured weekly
  - **A backlog is windowed, not truncated** (`max-versions-per-run`, default 25 — the review-stall threshold the consumer's own analyzer enforces). The excerpt is newest-first, so the old byte cap kept the newest bytes and dropped the oldest versions *while still ratcheting to the top of the range*, skipping them for good. Windowing instead keeps the **oldest** N versions after `lastCheckedVersion` and ratchets only to the top of that window; the next run continues from there because upstream's latest still exceeds the new tracked version. Downstream consumers must use the `effective_latest` output, never `latest_version`
  - **Token usage comes from the action's `execution_file`, never from full output** (issue #54). The job log cannot show cache hits: with `show_full_output` off the action logs only duration, turns, cost and denials, and `sanitizeModelUsage` strips token counts on purpose. The action writes every SDK message to `$RUNNER_TEMP/claude-execution-output.json` whatever `show_full_output` says, and `Summarise triage token usage` reduces it to numbers: a per-call table and the cache hit rate in the job summary, plus a numbers-only `changelog-triage-usage` artifact (90 days). Never turn on `show_full_output` or `display_report` for this on a public workflow. Totals come from the result message's `modelUsage`, which covers every API call; per-call rows come from assistant messages, **grouped by `message.id` with the per-field max**, because the SDK emits one assistant message per content block and repeats the usage; the gap between the two is printed. The step runs after publish under `!cancelled()` with `continue-on-error`, so it reports on a max-turns failure and can never gate publication; the upload (SHA-pinned like every other new `uses:`; the harness asserts it) sets `overwrite: true` because "Re-run failed jobs" re-uploads the same name. `just changelog-usage` runs the extracted step against fixtures, hostile values included

#### `reusable-claude-review.yml` has few callers, and a new one needs more than a caller file

Seven callers (claude-plugins, comfyui-nodes, dotfiles, loractl, mcu-tinkering-lab, pal-mcp-server, scansift) were `disabled_manually` between March and September 2026 while their files still declared `pull_request` triggers, and PRs opened on 2026-10-24 delete those files (claude-plugins#3198, dotfiles#511, mcu-tinkering-lab#863 and pal-mcp-server#212 merged; comfyui-nodes#254, loractl#255 and scansift#74 were still open on 2026-10-31). shore-recon added a caller on 2026-10-29 (shore-recon#82). Check `gh workflow list -R <repo>` before treating the list as current. Re-enabling it in a repo takes more than a new caller:

- **The bot gate.** `skip_bots` matches only `github-actions[bot]` (the job `if:` compares `github.actor` with that one login), despite the summary above, and `allowed_bots` defaults to `claude[bot],claude`. A Renovate or Dependabot PR therefore reaches the action and is refused as a non-human actor, a red check, as it was for `reusable-auto-fix.yml` in mcu-tinkering-lab. `skip_authors` does not cover this: it matches the PR author, and its default lists only the claude-config-sync App. Gate on any `[bot]` login not in `allowed_bots`, the rule the analysis workflows' `Check actor is allowed` step applies.
- **`actions: read` in the caller.** Since a8b2a00 (2026-09-25) the workflow requests `actions: read` for the action's github_ci MCP server. A caller whose `permissions:` block omits it grants none, and a reusable workflow that requests more than its caller grants fails at startup (`startup_failure`, no jobs). Five of the original seven callers declared explicit permissions without it, and shore-recon's did too.
- **The cost guard skips only Claude config by default.** `skip_paths` (default `.claude/**`, `.mcp.json`) can skip docs-only or lockfile-only PRs, but only if the caller extends it. No input caps the diff size before an opus review of up to 50 turns on every push.

#### The `additional_permissions` trap

`anthropics/claude-code-action`'s `additional_permissions:` input takes a **GitHub permissions map** — `actions: read` and nothing else. A Claude **tool list** written there is silently inert: no `allowedTools` reaches the SDK, the action's default policy denies the writes, and **the SDK exits 0 on a permission denial**, so the run goes green having done nothing. Three workflows here had it; `reusable-claude.yml` always had it right and is the canonical shape:

- tools go in an `allowed_tools` input (comma-separated), composed into `claude_args` as `--allowedTools "..."` — a **separate input from `claude_args`** on purpose, so a caller overriding `--model`/`--max-turns` cannot silently drop the tool grant. `reusable-changelog-review.yml` is the deliberate exception: its list is pinned inline and not caller-tunable, because the *exclusions* (`WebFetch`/`WebSearch`) are part of its prompt's contract that the pre-sliced excerpt is the only input
- `additional_allowed_tools` appends caller extras; `additional_permissions` is the permissions map only
- `--allowedTools` is **additive** over the action's defaults, so listing tools widens rather than restricts
- naming `TodoWrite` is a real grant, not decoration — since 2.1.233 the todo/task tools are off by default on current models and listing one is the session-wide opt-in
- diagnose from the job log's `SDK options:` block: `allowedTools` absent = broken

#### Claude-Powered Analysis Workflows

Security, quality, and accessibility workflows use `anthropics/claude-code-action` v1, pinned to a commit SHA. Each exposes `max-turns` (default 50), `model` (default `claude-opus-5-5`, except `claude-haiku-5-5` for `quality-typescript`, see below) and `effort` (default `low`, passed as `--effort`; `''` omits the flag) inputs:
- **Security**: `reusable-security-{secrets,owasp}.yml`
- **Quality**: `reusable-quality-{code-smell,typescript,async}.yml`
- **Accessibility**: `reusable-a11y-{aria,wcag}.yml`

All require `CLAUDE_CODE_OAUTH_TOKEN` secret. They analyze changed files in PRs and publish findings to the **job summary and PR file annotations** — never a PR comment. The action grants no comment tool, so a prompt asking Claude to comment only produced denials and discarded the findings (issue #47); `$GITHUB_STEP_SUMMARY` and `::warning`/`::error` both work under the `contents: read` these jobs already hold, and need nothing in `additional_permissions:`.

Eight things not to re-derive:
- **The file list runs in glob-pathspec mode** (`GIT_GLOB_PATHSPECS: '1'` on the file-list step). In git's default mode `*` crosses `/` but the literal `/` in `**/` must still match, so every `**/<x>` pattern, `**/*` included, dropped root-level files (`.env.example`, `.mcp.json`, a top-level `server.py`) and a root-only PR got the green "nothing was scanned" notice. Glob mode also means a bare `*.py` matches the root only, so caller patterns stay `**/`-prefixed. `.github/tests/changed-files-pathspec/run.sh` runs the extracted step on a scratch repo with root-level and nested files.
- **The publish block is byte-identical across all seven**, bar four env values (`TITLE`, `BLOCKING_SEVERITIES`, `COUNT_KEYS`, `NOTHING_SCANNED_REASON` — masked in the drift check, so a per-workflow message stays possible without forking the block). It is duplicated on purpose: `uses:` takes no expressions, so a shared composite action would execute at floating `@main` even for a consumer who pinned this repo by SHA, and a script under `.github/` is not checked out either (these jobs run `actions/checkout` with no `repository:`, so the workspace is the *caller's*). `scripts/check-publish-drift.sh` (`just publish-drift`) enforces the identity and fails on absence as well as drift.
- **Every gate predicate compares numerically** (`steps.publish.outputs.blocking > 0`), never as a string (`!= '0'`), and none carries `always()`. GitHub coerces the empty string a skipped publish step leaves behind to 0 for `>`, so a numeric gate cannot fire on a PR that scanned nothing; string comparison does the opposite and would take every consumer red on a README-only PR.
- **The fixture harness EXTRACTS the shipped block** out of a workflow with `awk`/`sed` rather than holding a retyped copy (`just publish-fixtures`). That is what caught the annotation-escaping, non-object-element and `index()`-scope defects; a retyped copy is not the code under test.
- **Everything the model emits is untrusted at the shell boundary**, `--json-schema` notwithstanding: the `enum` on `severity` and the `integer` on the counts are requests to the model, not constraints the runner applies. So annotation payloads (`severity` included) are `%`/CR/LF-escaped; `line` and the counts are type-checked, since a count carrying a newline writes a second `key=value` line into `$GITHUB_OUTPUT` and can overwrite `blocking`; and `findings` is shape-checked in the guard, because a non-array aborts jq under `set -e` and discards summary, annotations and outputs together.
- **The payload is read from `execution_file`, never from `structured_output` through env.** The publish block binds `EXECUTION_FILE: ${{ steps.analyze.outputs.execution_file }}` (the action's transcript at `$RUNNER_TEMP/claude-execution-output.json`, a JSON array of SDK messages) and extracts `[.[] | objects | select(.type == "result")] | last | .structured_output` into a file that every jq call reads. An env string of 131072 bytes or more (`MAX_ARG_STRLEN`) fails the execve of the step's own shell with E2BIG before line 1 runs, so a large scan published nothing, not even the degrade message (#61); passing it to jq via `--arg`/`--argjson` only moves that failure one exec later, and interpolating it into `run:` is the #57 injection. The fixtures obey the same rule: payloads reach jq on stdin and `env_under_cap()` refuses any over-cap export. Reading the transcript also recovers findings the env output never carried, since upstream sets `structured_output` only on a clean success: a result flagged `is_error` or one over `--max-turns` publishes with the "may be incomplete" warning, while an `error_*` result normally carries none and degrades. This is a contract with `claude-code-action` v1 at the commit pinned here, which each Renovate bump moves (its `execution_file` output and the array-of-messages shape, verified at cab360f), so an unset, missing, unparseable or reshaped file degrades loudly with zeroed counts rather than crashing the step. The degrade branch also writes `degraded=true` (only the success path writes `false`), and that is what keeps the read from failing *open*: under `--json-schema` an analyze outcome of `success` means the action had a `structured_output`, so a success that publish could not read lost a real report on this side, and its zeroed counts would skip every severity gate — `Classify analysis outcome` therefore fails any `success` run whose `degraded` is not exactly `false`
- **A missing `structured_output` is a warning, every other analysis failure is red.** With `--json-schema` the action fails the step whenever a `subtype: success` run returns no `structured_output`, and that happens at random on an unchanged SHA. So the `analyze` step is `continue-on-error: true`, and `Classify analysis outcome` (after the END marker, outside the drift-checked block, and before any severity gate, since its exit 1 is now what skips them) reads the last `result` message in `execution_file`: `success` + `!is_error` + no `structured_output` → `::warning`, job green; anything else → `::error` with the reason, job red. On an analyze outcome of `success` it reads no transcript and instead fails closed on the publish step's `degraded` output (above), so the green warning path is reserved for a run where Claude returned no `structured_output`, never for a scan whose output the workflow failed to read. `read` collapses an empty `@tsv` field (tab is IFS whitespace), which is why the `word` helper maps empty to `unknown`. Consequence for callers: on the warning path the job result is `success` **and every count output is `0`** (the publish block's degrade branch writes zeroed counts), so neither `result` nor a zero count means the scan ran clean — a gate like `result == 'success' && secrets-found == '0'` passes a PR that was never analysed. Only the `::warning` annotation and the job summary tell the two apart. `.github/tests/analysis-verdict/run.sh` (`just analysis-verdict`) extracts the shipped step body and runs it against fixture execution files, runs the shipped publish step on the warning path to pin the zeroed counts, chains shipped publish into shipped verdict on a `success` outcome with an unset, empty, reshaped or result-less execution file to pin the fail-closed path, and asserts the body is identical across every `--json-schema` workflow; `.github/tests/analysis-contract/run.sh` (`just analysis-contract`) pins the schema, prompt and gates.
- **push is refused, not scanned.** claude-code-action v1 throws `Unsupported event type` for any event outside the `switch` in its `src/github/context.ts` (issues, issue_comment, pull_request, pull_request_target, pull_request_review, pull_request_review_comment, workflow_dispatch, repository_dispatch, schedule, workflow_run), so a caller with a `push` trigger got a red check that read like a leak (issue #63, comfyui-nodes#162). The first step, `Check trigger is supported` (id `event`, no `if:`), matches that list and writes `supported` / `unsupported`; checkout, the file list and `analyze` all compare `supported == 'true'`, a string equality, so an unset output fails closed — never `!= 'false'`. The shared `Report that nothing was scanned` step then names the refused trigger through `UNSUPPORTED_EVENT`, so the job is green with one notice. Only `pull_request` yields a meaningful range: the `HEAD~1` branch stays because workflow_dispatch and schedule reach it (deleting it, the issue's option 1, would break them), and the other allowlisted events also land there and scan the default-branch tip. `pull_request_target` deliberately stays on that path: checkout has no `ref:`, so it diffs the base, and checking out the PR head in a job holding `CLAUDE_CODE_OAUTH_TOKEN` and `id-token: write` is a pwn-request. The list is a copy of the pinned v1 release's: if a later release adds `push`, the guard keeps refusing it green until the list is updated. `.github/tests/event-guard/run.sh` (`just event-guard-fixtures`) extracts the step and checks the wiring; the report text is in `just publish-fixtures`. A bot actor that `allowed-bots` does not list is refused the same way: the action throws "Workflow initiated by non-human actor", which took every Renovate PR red in a caller without its own `if:` (comfyui-nodes), so `Check actor is allowed` (id `actor`) applies the action's rule first (a login ending in `[bot]` is a bot; names compare lowercase with spaces and the suffix dropped; `*` admits all), every step up to `analyze` requires `allowed == 'true'`, and the report names the actor through `REFUSED_ACTOR`. The action decides by account type, so a bot whose login lacks `[bot]` still reaches it. The step applies the same rule to the PR **author** (`AUTHOR: ${{ github.event.pull_request.user.login }}`, empty outside a PR event) and writes `refused_author`, which the report names through `REFUSED_AUTHOR`: the action checks only the actor, so a human reopening or pushing to the claude-config-sync App's PR made security-secrets run Claude on `**/*` over files that are only Claude config (laurigates/gitops#341). A human push to a Renovate PR is now skipped the same way unless `allowed-bots` lists the bot. `.github/tests/actor-guard/run.sh` runs the extracted step against the action's rule.

**`reusable-quality-typescript.yml` reports the grep-able Critical tier from a shell step, not from Claude** (issue #83). `TypeScript critical patterns` (id `tscritical`) runs before the analysis and annotates explicit `any` written after `:`, `<`, `,`, `|`, `&`, `=`, `[` or `as` (so `Record<string, any>`, `string | any` and `type T = any` too), `@ts-ignore`, a bare `@ts-expect-error`, `@ts-nocheck` and the non-null assertions a regex can tell from `!==` (`x!.`, `x![`, `x!)`), with string literals emptied first; the prompt lists exactly those positions, tells Claude not to report or count them, and keeps it on every other explicit-`any` form as Critical (keep the prompt's list and the regex in step), and the `any-count` output reads the step's `any_count`, so it no longer comes from Claude and is set even when Claude is skipped or degrades (`issues-found` still comes from Claude, and now excludes these hits). It is advisory and fails only on an unreadable pull-request diff range; on `workflow_dispatch`/`schedule` with no `HEAD~1` it scans nothing and stays green, like the `changed` step. It lists the PR's files itself (`git diff -z`) instead of reading `steps.changed.outputs.files`, because that list is capped at `file-limit` and narrowed after a clean scan, and a hit in an unchanged file must still be reported on every head. `.github/tests/ts-critical-patterns/run.sh` runs the extracted step against fixtures. Its `model` defaults to `claude-haiku-5-5` (issue #83). The extracted prompt and schema were run through headless `claude -p` at `--effort low` against a seeded fixture, three repetitions per model. Haiku 5.5 found all 8 seeded High/Critical defects the shell step leaves to Claude in 3 of 3 runs, as Opus 5.5 did, at about 1/27 of the cost ($0.011 vs $0.296 a run) and 23 turns against 5. `reusable-a11y-aria.yml` and `reusable-quality-code-smell.yml` stay on Opus: Haiku's graded runs found 0.30 and 0.61 of their seeded High/Critical defects against Opus's 1.00 and 0.94, reported line numbers past the end of the file, and an ungraded diagnostic rerun found all of them, so its results there vary from run to run.

**`reusable-security-secrets.yml` also runs a `gitleaks` job** beside the Claude scan, with no actor gate, size cap or file patterns, so bot PRs and PRs over `max-diff-lines` are still scanned. It installs a SHA256-pinned gitleaks on `ubuntu-slim` and fails on a finding. Two things not to re-derive: a `.gitleaks.toml` with only an `[allowlist]` loads zero rules and gitleaks prints no rule count, so a step first requires the config to detect two keys planted in a scratch directory (and exports it as `GITLEAKS_CONFIG`, so the scan loads the same file); and `gitleaks git` exits 0 on a range with no commits, a missing base ref included, so the scan resolves and counts the range first. A push with no usable `before` (a new branch, a force-push), `schedule` and `workflow_dispatch` scan `origin/<default>..HEAD` (issue #111). When that range is empty, a non-fast-forward push whose `before` resolves scans `merge-base(before, after)..after`, every commit the force-push introduced; this is the force-push to the default branch itself, where `origin/<default>` is the new head (issue #125). A force-pushed-away `before` is reachable from no ref, so `actions/checkout` never fetches it: the `Fetch the push base` step asks the remote for it by SHA, with `github.token` passed as one-command git config (`GIT_CONFIG_COUNT`) because `persist-credentials: false` removed checkout's credential, and the scan step holds no token. Only when the fetch fails (itself a `::notice`), the rewrite shares no merge base with `before`, or the default branch does not resolve does the scan fall back to the last commit, with a `::notice` and a summary line saying earlier commits were not scanned. On `pull_request` the config and `.gitleaksignore` come from `origin/<base>`, never the PR head (issue #112): a base without a config gets a default-only `[extend] useDefault = true` file, because gitleaks auto-loads `<source>/.gitleaks.toml` whenever `GITLEAKS_CONFIG` is unset, and the head's `.gitleaksignore` is deleted from the checkout before the scan, because gitleaks loads `<source>/.gitleaksignore` on top of `--gitleaks-ignore-path` (v8.30.1 `cmd/root.go`). gitleaks resolves a relative `[extend] path` against its working directory, not against the config file, so both the config check and the scan run gitleaks from `GITLEAKS_ROOT` (issue #124). On `pull_request` that is a directory holding only the files the base config's extend chain names (gitleaks follows at most two links), copied from `origin/<base>` at their repository paths, read with Python's `tomllib`; an absolute path, one that leaves the repository, or one the base does not have is an `::error`, since each could name a file in the PR's checkout. A link `tomllib` cannot read is not copied and then fails to load from `GITLEAKS_ROOT`, so it fails closed. Other events, a push after review among them, use the checked-out files and run from the checkout, and every event exports `GITLEAKS_CONFIG`, `GITLEAKS_IGNORE_PATH` and `GITLEAKS_ROOT`; the scan refuses to run without them. An inline `gitleaks:allow` comment stays a bypass the PR controls. `.github/tests/gitleaks-guard/run.sh` runs the extracted steps against scratch repos, through the shipped install step on Linux x86_64.

**A push to an open PR re-scans only the PR files it changed, when the previous head was scanned clean.** The seven file-pattern workflows key a one-byte cache marker on the PR head (`analysis-clean-v1-<scan>-<hash of every input>-<sha>`). `Check whether this scan was clean` and `Record a clean scan`, the job's last two steps, write it only when every step passed and Claude analysed every file it was given with no finding and no non-zero count, or when no PR file had changed. On `synchronize`, `Look up a clean scan of the previous head` (`lookup-only`) and `Get changed files` narrow the list to the PR files in `before..head`, intersected with the PR's own files, so a merge from the base adds nothing. A missing marker, a force-push or a failed lookup falls back to the whole PR. "The previous run succeeded" is no proof: the diff-size and no-match skips are green too. A cache a PR run writes is readable by that PR's later runs and by no other PR, and the cache needs no `actions:` permission; listing earlier runs through the API would, and every caller that does not grant it would hit a startup failure. `.github/tests/incremental-rescan/run.sh` runs the extracted steps on a scratch history (an edit, a merge from the base, a force-push).

### OpenCode-Powered Workflows

Both need the `OPENCODE_API_KEY` secret, which gitops pushes to repos flagged `opencode = true`.

- **`reusable-opencode-review.yml`** — automatic review of each pull request with an OpenCode model (default `opencode/glm-5.3-flash-free`: free on OpenCode for a limited time, and OpenCode states its provider keeps no data and does not train on it). A caller runs `on: pull_request` (opened, synchronize, reopened, ready_for_review), grants `contents: read` and `pull-requests: write`, and passes `secrets: OPENCODE_API_KEY`. Before any model call it skips, each with a `::notice`: drafts; bot actors and bot-authored PRs (Renovate, release-please, Dependabot, github-actions) unless `allowed-bots` lists them; fork PRs, which get no secrets; PRs whose every file matches `skip-paths` (docs and lockfiles by default); on `synchronize`, commits since the last posted review that change no reviewable PR file; and diffs over `max-diff-lines` (also written to the job summary). It fails red, never green, on a non-`pull_request` event, an empty or rejected key, a model OpenCode no longer lists, an agent that is not read-only, and a run that writes no valid findings file. `.github/tests/opencode-review/run.sh` runs each step's shipped body against fixture payloads.

  Details worth not re-deriving:
  - **The CLI, not `anomalyco/opencode/github`.** The action accepts `pull_request` (next entry), but its `action.yml` installs the latest CLI release at run time whatever SHA it is pinned to, and on a PR it commits and pushes any change the agent leaves in the working tree to the PR branch. This workflow downloads `OPENCODE_VERSION` and checks `OPENCODE_SHA256`; a bump edits both.
  - **The model can read the checkout and write `.opencode-review/findings.json`, nothing else.** `OPENCODE_PERMISSION` starts with `"*": "deny"` (opencode applies the last matching rule), and `OPENCODE_DISABLE_PROJECT_CONFIG` ignores any `opencode.json` or `.opencode/` the PR carries. opencode drops an invalid `OPENCODE_PERMISSION` with only a log warning and then enables every tool, so `Check the agent is read-only` evaluates the rules `opencode debug agent build` resolves and fails unless bash, webfetch and edits outside the findings file are denied. No GitHub token is in the model's environment; the publish step posts, after validating the file.
  - **One review per run.** A finding on a right-side diff line becomes an inline comment (`inline-comments: false` puts every finding in the body); the others and a short summary go in the review body. Under the default ruleset's required conversation resolution, each inline comment must be resolved before the PR can merge, auto-merge included. A 422 on the inline comments retries once with all findings in the body.
  - **Incremental re-review.** The review body ends with `<!-- opencode-review:reviewed=<head sha> -->`. On `synchronize` the diff runs from the last such marker in a `github-actions[bot]` review to the new head (compare API), limited to the PR's own files, so a merge from the base branch adds nothing, and a push whose run `cancel-in-progress` cancelled is covered by the next run.
  - The key and model check runs before the file gates, so a repo whose secret is lost fails on its next human PR, docs-only ones included.

  - The job's `if:` is a deliberately loose `contains()` pre-filter; a **guard step** then requires `/oc` or `/opencode` as a whole token and skips the action when the mention is only a substring (`/october`). Without it, such a comment runs the agent: the handler matches mentions with a substring test. The comment body reaches the guard via `env:`, never interpolated into the script — it is attacker-controlled.
  - The action is pinned to a release SHA, but **pinning does not fully close the floating-version exposure**: `action.yml`'s first step `curl`s the *latest* opencode CLI release at runtime regardless of the pin. The pin covers the wrapper, not the binary it installs. Fix proposed upstream in [anomalyco/opencode#39147](https://github.com/anomalyco/opencode/pull/39147) — runs the installer bundled at the pinned ref and adds a `version` input passed to the installer. **That PR was auto-closed on 2026-08-28 and the caveat is therefore open-ended, not pending.** It was closed by upstream's PR-cleanup bot on its stated criteria — older than a month, fewer than two positive reactions (the PR has zero) — not on review; a reopen request the same day is unanswered. The branch `fix/pin-installer-and-cli-version` is intact and the linked issue [#39163](https://github.com/anomalyco/opencode/issues/39163) is still open, so closing the gap means getting the PR reopened (reactions are the bot's own criterion) or refiling it.   | Caller event | Job | Does |

  | `push` to the default branch | `provision` | Creates, updates or renames the `build:` and `area:` labels that `.github/issue-labels.json` defines. Deletes nothing. No taxonomy file: a notice, exit 0 |

  | `pull_request` opened, synchronize, reopened, edited | `classify-pr` | Adds the type label from the title and a routing label per changed file; `edited` re-classifies after a title change.   The model stage for issues the classifier leaves unlabelled is not built (#147). Six things not to re-derive:
  - **Every write uses `github.token`, and that is what prevents a loop.** A label written with it starts no workflow, so neither this workflow nor a caller that listens for label events (merge-method) runs again. A PAT or App token here would make each label write an event
  - **The calling repository is never checked out.** The only checkout is the script, from laurigates/claude-plugins. The taxonomy is read through the contents API at the default branch and titles and bodies through the API by number, so a pull request cannot change the taxonomy that labels it, and no `run:` body holds an expression. The head branch name reaches the `skip-heads` gate through `env:`
  - **Additive, and only labels that exist.** The steps send `add` from the script's `classify` output and nothing else: a label whose group (type, or one routing prefix) is still empty on the item and which the repository has. Adding a missing label to an issue through REST would create it. The standard labels (`core:*`, `needs:*`, `blocked`, the type labels) come from laurigates/gitops `labels.tf`; `provision` writes `build:` and `area:` only. No step edits a title or body
  - **A step writes only when `dry-run` is exactly `false`.** Any other value, an unset one included, prints what would change. For `provision` and `unblock` that is the script's `--dry-run`
  - **One caller grant, narrower per job.** The caller grants `contents: read`, `issues: write`, `pull-requests: write`. A job that asks for more than the caller grants fails the run at startup on every event, including events that job does not run on, so a new scope here (`id-token: write` for a model stage) breaks every caller until each one grants it
  - **The audit issue is filed once and commented on only when the findings change.** It is found by exact title among open issues opened by `github-actions[bot]` (`app/github-actions` in `gh issue list --json author`), so an issue anyone else opens with that title is not adopted. A hidden marker holds a hash of the (finding type, issue number) pairs, and a run whose hash equals the latest marker posts nothing. Issue numbers are in a code block, because a linked number would add a cross-reference to every listed issue on each report; the job summary has the links. It is closed by hand, and the next audit with findings files a new one

## Testing

`.github/workflows/lint.yml` gates every PR and push to `main`: YAML validity, actionlint, shellcheck over the tracked `*.sh`, the publish-block drift check, a scratch-dir `rulesync generate`, and `bash .github/tests/run.sh`, which discovers and runs every `.github/tests/<name>/run.sh`. Locally:

```bash
just lint                     # yq YAML check + actionlint + shellcheck (warning severity) on tracked *.sh, at the pinned versions
just rules-check              # lint.yml's rulesync step: generate in a scratch copy, never at the root
just test                     # every test, via .github/tests/run.sh
just test workflow-contract   # only the named test(s)
```

A test passes only if it exits 0 **and** its last output line starts with `PASS: ` (print `PASS: <name> (<n> assertion(s))`); an exit-0 test without that line is reported FAIL, because it may have stopped before asserting anything, and the runner fails when it discovers no tests. A new test therefore needs no lint.yml step, and must not get one: `workflow-contract` rejects a step that runs a single test. Conventions are in `.github/tests/README.md`. The per-test recipes (`just publish-fixtures`, `just autofix-fixtures`, …) stay for running one harness against a non-default workflow path. Tests that guard the repo as a whole rather than one workflow:

- **`runner`** — the runner itself, against fixture tests in scratch repos: a test that reads stdin (or fd 3, where the runner keeps the list) cannot swallow the tests after it, a failing test is still reported after one, and a run whose count differs from the discovered count fails. Each test gets stdin from `/dev/null`; before that, a stub `gh` doing `cat > file` would have consumed the rest of the list and the runner would have printed "All 1 test(s) passed." with exit 0
- **`workflow-contract`** — every `reusable-*.yml` declares `workflow_call` and a top-level `permissions:` map; lint.yml runs the runner unconditionally and sets `persist-credentials: false` and `timeout-minutes`; every `uses: laurigates/.github/.github/{workflows,actions}/…` in a tracked file names something that exists here; and every `uses:` in a tracked workflow or composite action is `owner/repo[/path]@<40-hex SHA>` followed by a `# vX.Y.Z` comment, except this repo's own workflows and actions at `@main` and local `./` actions, so a tag, branch or short-SHA ref fails (#154). It finds each value with yq and reads the comment from that raw line
- **`tool-pins`** — every rulesync run through npx carries one exact `@X.Y.Z` version (lint.yml and `reusable-sync-ai-rules.yml` both run it), and lint.yml's `ACTIONLINT_VERSION` / `SHELLCHECK_VERSION` equal the justfile's `actionlint_version` / `shellcheck_version`, each download checked against its `*_SHA256`. Nothing tracks these automatically (Renovate runs here, but none of its managers, nor `renovate.json`'s Claude model manager, reads them), so a bump edits every site
- **`sync-ai-rules-targets`** — the shipped `rulesync generate` passes `--targets`/`--features` equal to `rulesync.jsonc` and `fetch` passes `--path .rulesync`, the two exit-0-with-zero-files traps; the fetch step also binds `GITHUB_TOKEN`, because an anonymous fetch shares the hosted runners' 60-requests-an-hour limit and fails intermittently
- **`rulesync-ignore`** — `.rulesync/.aiignore` covers no tracked file, in particular not `.rulesync/` or `rulesync.jsonc`. Every line there becomes a `Read(...)` deny in each consumer's generated `.claude/settings.json`, which also blocks Edit, Write and path-naming Bash, so listing the rule source made it uneditable wherever it was synced
- **`claude-action-permissions`** — `additional_permissions` is a permissions map (see the trap above), and a claude-code-action step that can run in tag mode, or allows `mcp__github_ci__*`, has `actions: read` on the job token
- **`issue-labels-taxonomy`** — `.github/issue-labels.json` passes the script's `check_taxonomy` rules for provisioning, uses only glob forms that git's glob pathspec and the script's matcher read alike, has no glob that matches no tracked file and no scope shared by two labels, and routes every reusable workflow, action and test. The script reads a stale glob or scope as "no label" and says nothing, and a new workflow or test without routing fails here

## Conventions

- **Commit messages**: [Conventional Commits](https://www.conventionalcommits.org/) — `type(scope): description`
- **Action pinning**: actions are pinned to full SHA with version comment (e.g., `actions/checkout@<sha> # v6.0.2`); this repo's own workflows and actions stay at `@main`. `workflow-contract` enforces both
- **Concurrency groups**: workflows use concurrency groups to prevent racing (e.g., `release-please-${{ github.repository }}`)
- **Secret fallbacks**: workflows use `${{ secrets.CUSTOM_PAT || secrets.GITHUB_TOKEN }}` pattern for optional PATs
- **Permissions**: each workflow declares minimal `permissions` at workflow level
