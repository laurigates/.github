# OpenCode-Powered Workflows

Both need the `OPENCODE_API_KEY` secret, which gitops pushes to repos flagged `opencode = true`.

- **`reusable-opencode-review.yml`** — automatic review of each pull request with an OpenCode model (default `opencode/deepseek-v4.1-flash-free`: free on OpenCode for a limited time, and OpenCode states its provider keeps no data and does not train on it). A caller runs `on: pull_request` (opened, synchronize, reopened, ready_for_review), grants `contents: read` and `pull-requests: write`, and passes `secrets: OPENCODE_API_KEY`. Before any model call it skips, each with a `::notice`: drafts; bot actors and bot-authored PRs (Renovate, release-please, Dependabot, github-actions) unless `allowed-bots` lists them; fork PRs, which get no secrets; PRs whose every file matches `skip-paths` (docs and lockfiles by default); on `synchronize`, commits since the last posted review that change no reviewable PR file; and diffs over `max-diff-lines` (also written to the job summary). It fails red, never green, on a non-`pull_request` event, an empty or rejected key, a model OpenCode no longer lists, an agent that is not read-only, and a run that writes no valid findings file. `.github/tests/opencode-review/run.sh` runs each step's shipped body against fixture payloads.

  Details worth not re-deriving:
  - **The CLI, not `anomalyco/opencode/github`.** The action accepts `pull_request` (next entry), but its `action.yml` installs the latest CLI release at run time whatever SHA it is pinned to, and on a PR it commits and pushes any change the agent leaves in the working tree to the PR branch. This workflow downloads `OPENCODE_VERSION` and checks `OPENCODE_SHA256`; a bump edits both. Renovate opens the version bump (#166, `workflow-renovate.md`), and that PR is green with the old hash, because `opencode-review` installs a stub tarball with its own hash and no test downloads the real release, so `OPENCODE_SHA256` is replaced on it before merging.
  - **The model can read the checkout and write `.opencode-review/findings.json`, nothing else.** `OPENCODE_PERMISSION` starts with `"*": "deny"` (opencode applies the last matching rule), and `OPENCODE_DISABLE_PROJECT_CONFIG` ignores any `opencode.json` or `.opencode/` the PR carries. opencode drops an invalid `OPENCODE_PERMISSION` with only a log warning and then enables every tool, so `Check the agent is read-only` evaluates the rules `opencode debug agent build` resolves and fails unless bash, webfetch and edits outside the findings file are denied. No GitHub token is in the model's environment; the publish step posts, after validating the file.
  - **One review per run.** A finding on a right-side diff line becomes an inline comment (`inline-comments: false` puts every finding in the body); the others and a short summary go in the review body. Under the default ruleset's required conversation resolution, each inline comment must be resolved before the PR can merge, auto-merge included. A 422 on the inline comments retries once with all findings in the body.
  - **Incremental re-review.** The review body ends with `<!-- opencode-review:reviewed=<head sha> -->`. On `synchronize` the diff runs from the last such marker in a `github-actions[bot]` review to the new head (compare API), limited to the PR's own files, so a merge from the base branch adds nothing, and a push whose run `cancel-in-progress` cancelled is covered by the next run.
  - The key and model check runs before the file gates, so a repo whose secret is lost fails on its next human PR, docs-only ones included.

- **`reusable-opencode.yml`** — enables `/opencode` (or `/oc`) mentions in issue comments and PR review comments, via `anomalyco/opencode/github`.

  **The action is not mention-only.** Its `action.yml` runs `opencode github run`, whose handler (`packages/opencode/src/cli/cmd/github.handler.ts`, `SUPPORTED_EVENTS`) accepts `issue_comment`, `pull_request_review_comment`, `issues`, `pull_request`, `schedule` and `workflow_dispatch`. `github/index.ts`, whose `assertContextEvent("issue_comment", "pull_request_review_comment")` this entry used to cite as proof that no automatic-review mode exists, is not what the action runs (checked at v1.19.3 and v1.19.4). This workflow wires only the two comment events; automatic review is `reusable-opencode-review.yml`.

  Two details worth not re-deriving:
  - The job's `if:` is a deliberately loose `contains()` pre-filter; a **guard step** then requires `/oc` or `/opencode` as a whole token and skips the action when the mention is only a substring (`/october`). Without it, such a comment runs the agent: the handler matches mentions with a substring test. The comment body reaches the guard via `env:`, never interpolated into the script — it is attacker-controlled.
  - The action is pinned to a release SHA, but **pinning does not fully close the floating-version exposure**: `action.yml`'s first step `curl`s the *latest* opencode CLI release at runtime regardless of the pin. The pin covers the wrapper, not the binary it installs. Fix proposed upstream in [anomalyco/opencode#39147](https://github.com/anomalyco/opencode/pull/39147) — runs the installer bundled at the pinned ref and adds a `version` input passed to the installer. **That PR was auto-closed on 2026-08-28 and the caveat is therefore open-ended, not pending.** It was closed by upstream's PR-cleanup bot on its stated criteria — older than a month, fewer than two positive reactions (the PR has zero) — not on review; a reopen request the same day is unanswered. The branch `fix/pin-installer-and-cli-version` is intact and the linked issue [#39163](https://github.com/anomalyco/opencode/issues/39163) is still open, so closing the gap means getting the PR reopened (reactions are the bot's own criterion) or refiling it. Re-verified at v1.19.4 on 2026-10-25: `github/action.yml` still resolves `releases/latest` and pipes `https://opencode.ai/install` to bash.

  Auth defaults to the OpenCode App OIDC exchange (`id-token: write`), which needs the [opencode-agent App](https://github.com/apps/opencode-agent) installed on the calling repo; set `use_github_token: true` to use `GITHUB_TOKEN` instead. Note the action requires the commenting actor to hold **write or admin** permission, so outside contributors cannot drive it.
